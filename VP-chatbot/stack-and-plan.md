## 0. Что изменилось относительно черновика

- **Сущность Bot.** Проект — то, что редактирует автор. Бот — опубликованная сущность: своя копия сценария, переменные окружения, статус, подключения к мессенджерам. На один проект можно создать несколько ботов (изоляция клиентов, multi-tenancy). Токен хранится у подключения бота, а не у проекта; у проекта больше нет «черновика и опубликованной версии».
- **Переменные окружения.** Новая сущность EnvironmentVariable (имя, значение, признак секрета, зашифрованное значение). Окружение есть у бота (рабочее) и у проекта (тестовое, только для превью). В шаблонах и выражениях переменная окружения записывается как `{{env.ИМЯ}}`.
- **Таймер убран.** Тайм-аут и повторы HTTP-запроса выполняет библиотека HTTP-клиента внутри ExternalApiClient. Отложенные задания BullMQ и TimerGateway для этого больше не нужны.
- **Разбор ответа.** Ответ внешней системы разбирается как JSON (ResponseParser); отдельные поля попадают в переменные по правилам ResponseMapping (jsonPath → имя переменной).
- **Очередь.** В черновике была «группировка по chatId в BullMQ». Группы — функция платной версии BullMQ Pro. Решено: очередь разбита на 16 разделов по ключу диалога (п. 2.2), бесплатная версия BullMQ.
- **Выражения.** Решено: вместо библиотеки `expr-eval` — свой интерпретатор над разборщиком `jsep` (п. 1.7).
- **Модель данных.** Решено: сценарий хранится целиком в JSONB (раздел 3).
- **План.** Защита в конце декабря 2026. До неё — три двухнедельных спринта и урезанный MVP: движок, HTTP-блок, Telegram, минимальный редактор, публикация, полное превью, экспорт и импорт JSON (раздел 5).
- **Хостинг.** Решено: недорогой VPS, Docker Compose и Caddy с сертификатом Let's Encrypt (п. 1.11).

## 1. Ключевые элементы платформы

### 1.0. Общая схема

Процессы, которые запускаются в Docker Compose:

| Процесс | Что делает | Классы модели |
| --- | --- | --- |
| web | Одностраничное приложение: редактор, превью, личный кабинет | EditorUI, PreviewChatUI, AccountUI |
| api | REST API, приём webhook мессенджеров, Socket.IO для превью | AuthController, ProjectController, ScenarioEditor, ScenarioValidator, PublicationController, ImportExportController, PreviewController, MessengerGateway (приём) |
| engine | Воркеры очереди событий, движок диалогов, HTTP-клиент | EventDispatcher, DialogEngine, HttpRequestExecutor, ResponseParser, ExpressionEvaluator, ExternalApiClient, MessengerGateway (отправка), SecretVault |
| postgres | Авторы, проекты, боты, контексты диалогов, журнал HTTP-запросов | Entity-классы |
| redis | Очередь событий (BullMQ), канал pub/sub для превью | — |
| caddy | Обратный прокси с HTTPS (Let's Encrypt) перед api и web; нужен для webhook Telegram | — |

Путь события: мессенджер → api (webhook) → очередь в Redis → engine → PostgreSQL. HTTP-запросы движка уходят во внешние системы из engine. Сообщения превью идут из engine через Redis pub/sub в api, а оттуда по Socket.IO в браузер.

Критерии выбора во всех таблицах:

- **соответствие требованиям** (Use cases, Vision);
- **порог входа для команды**: проекту уделяют около одного дня в неделю, на изучение сложных технологий времени нет;
- **один язык, без «зоопарка» технологий** — пожелание команды с семинара 28.10;
- **зрелость и лицензия**: библиотека сопровождается, бесплатна для учебного проекта.

### 1.1. Язык и рантайм

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **TypeScript на Node.js** | Один язык для фронта и бэка, общие типы блоков и событий; асинхронный ввод-вывод подходит движку, который в основном ждёт сеть; зрелые библиотеки для Telegram, очередей, холста | Однопоточный рантайм: тяжёлые вычисления блокируют цикл событий (у нас их нет) |

| Kotlin или Java (Spring Boot) | Строгая типизация, мощная экосистема | Два языка; дольше старт и больше шаблонного кода при одном дне в неделю |

**Выбор: TypeScript (strict) на Node.js 22 LTS.** Типы сценария (Block, Output, Transition, ResponseMapping) описываются один раз в общем пакете и используются редактором, API и движком. ### 1.3. Очередь событий и обработка диалогов

Требование (Use cases, п. 2.4): события одного диалога обрабатываются по очереди в порядке поступления; разные диалоги — независимо.

| Вариант | Порядок в диалоге | Плюсы | Минусы |
| --- | --- | --- | --- |
| **BullMQ + Redis, очередь разбита на разделы** | Событие попадает в раздел по хешу ключа диалога; раздел обрабатывается строго по одному заданию | Библиотека для Node.js, Redis прост в развёртывании; повторы, мониторинг, дедупликация заданий | Порядок обеспечиваем сами разделением на разделы; группы по ключу есть только в платной BullMQ Pro |
| RabbitMQ | Single active consumer или consistent-hash exchange | Настоящий брокер, гибкая маршрутизация | Отдельный сервер, новая технология для команды |
| Kafka | Ключ сообщения = ключ диалога, порядок внутри раздела | Порядок по ключу «из коробки» | Тяжёл в эксплуатации, избыточен для учебного проекта |
| Очередь в PostgreSQL (pg-boss, `SKIP LOCKED`) | Блокировка строки диалога | Без Redis | Нагружает основную базу; порядок всё равно реализуем сами |

**Решено: BullMQ (бесплатная версия) + Redis, 16 разделов (п. 2.2).** Ответ на вопрос куратора с семинара 28.10: BullMQ — не отдельный брокер, а библиотека очередей для Node.js. Брокером служит Redis: он хранит задания, а BullMQ даёт воркеры, повторы, отложенные задания и дедупликацию. RabbitMQ или Kafka пришлось бы поднимать и изучать отдельно. Redis запускается с журналом AOF, чтобы задания переживали перезапуск.

Обработка задания короткая: движок не ждёт внешние системы внутри задания (п. 1.5). Поэтому строгий порядок внутри раздела не тормозит остальные диалоги. Порядок и отсутствие блокировок проверяем коротким прототипом П1 в первом спринте.

### 1.5. HTTP-клиент с тайм-аутом и повторами (ExternalApiClient)

После семинара 28.10 таймер не моделируется: тайм-аут и повторы — деталь HTTP-библиотеки. ExternalApiClient получает `send(request, timeoutSec, retryCount, retryIntervalSec)` и по итогу сообщает `onResponse` (событие RESPONSE_RECEIVED) или `onFailure` (событие REQUEST_FAILED).

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **undici (`request`/`fetch`) + p-retry** | undici — штатный HTTP-клиент Node.js, тайм-аут через `AbortSignal.timeout`; p-retry — маленькая библиотека повторов с фиксированным интервалом; повторяем любые методы, как настроил автор | Две зависимости вместо одной; восстановление после падения процесса пишем сами |
| undici + своя обёртка повторов (около 30 строк) | Нет лишних зависимостей, полный контроль | Свой код нужно покрыть тестами |
| got | Тайм-аут и повторы встроены | По умолчанию не повторяет POST; пакет только ESM; ещё одна крупная зависимость |
| axios + axios-retry | Популярен | Тайм-аут axios не покрывает зависание соединения так же надёжно, как AbortSignal; две зависимости |
| Отдельная очередь BullMQ для HTTP-запросов (attempts + backoff) | Повторы переживают перезапуск процесса | Возвращает «таймер» на уровень очередей — то, что куратор предложил убрать из модели; сложнее |

**Выбор: undici + p-retry внутри ExternalApiClient** (своя обёртка — равноценная замена, если команда не хочет зависимость). Интервал повтора фиксированный, как в настройке блока (UC-A-14).

**Почему воркер очереди не блокируется на время ожидания и повторов:**

1. Задание очереди не ждёт ответа. HttpRequestExecutor сохраняет Request, переводит диалог в WAITING_EXTERNAL, фиксирует транзакцию и вызывает `send(...)` без `await`. На этом задание завершается, и раздел очереди свободен для следующих событий.
2. Ожидание ответа и пауза между повторами в Node.js — это открытый сокет и таймер цикла событий. Поток при этом не занят: тысячи ожидающих запросов стоят только памяти.
3. Результат возвращается в систему так же, как любое внешнее событие: `onResponse`/`onFailure` ставит в очередь RESPONSE_RECEIVED или REQUEST_FAILED с `requestId`, и оно обрабатывается в порядке событий своего диалога.

**Решено: восстановление после падения engine.** Незавершённые запросы теряются при падении процесса. При старте запросы в статусе SENT от прошлого запуска помечаются FAILED с текстом «запрос прерван перезапуском», и для них ставится REQUEST_FAILED — дальше работает стратегия ошибок блока. Повторно такой запрос автоматически не отправляется: POST может быть небезопасно повторять, например при бронировании.

### 1.6. Мессенджер-адаптер (MessengerGateway)

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **grammY** | Современная, типизированная, активно сопровождается; удобный режим webhook для многих ботов в одном процессе | — |
| Telegraf | Популярна, много примеров | Типы и сопровождение слабее, чем у grammY |

| Вариант | Плюсы | Минусы |

**Выбор: grammY, webhook** по маршруту `/webhook/telegram/{botId}` с секретом `secret_token` (заголовок, который Telegram передаёт с каждым обновлением). Long polling — только для локальной отладки.

### 1.7. Вычисление выражений и шаблонов (ExpressionEvaluator)

Выражения нужны в блоках «Присваивание» (`tries + 1`) и «Условие» (`tries < 3`). Шаблоны `{{имя}}` — в тексте сообщений, URL, заголовках и теле HTTP-запроса.

Выражения:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **jsep + свой интерпретатор AST** | jsep только разбирает выражение в дерево и ничего не исполняет; вычисляем сами по белому списку узлов и операторов — нет доступа к объектам JS | Интерпретатор около 150 строк, нужны тесты |
| Свой разборщик с нуля | Полный контроль над грамматикой | Больше кода, чем с jsep |
| expr-eval (было в черновике) | Готовое решение | Давно не сопровождается; в 2025 г. в нём найдены уязвимости, позволяющие выполнить код на сервере (CVE-2025-12735, CVE-2025-13204) |
| mathjs | Мощная, сопровождается | Тяжёлая; лишние возможности приходится отключать |
| `eval` / `new Function` | — | Недопустимо: выражения пишет автор, это выполнение чужого кода на сервере |

Шаблоны:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Своя подстановка `{{имя}}`** | Совпадает с методами модели `extractVariableNames` + `substitute`; легко экранировать по месту (URL, JSON, заголовок) | — |
| Handlebars / Mustache | Готовые циклы и условия | Логика в шаблонах не нужна — для неё есть блоки; экранирование рассчитано на HTML |

**Решено: jsep + свой интерпретатор для выражений, своя подстановка для шаблонов** (алгоритмы — п. 2.4 и 2.5). Переменные окружения и в шаблонах, и в выражениях записываются как `{{env.ИМЯ}}`.

### 1.8. Хранение секретов (SecretVault)

Секреты: токены мессенджеров, секретные заголовки HTTP-блока и секретные переменные окружения (ключи API). Vision: «шифруются при записи и не отображаются обратно».

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **AES-256-GCM средствами `node:crypto`, ключ из переменной окружения** | Без внешних сервисов; аутентифицированное шифрование — подмена шифротекста обнаруживается | Ключ лежит в окружении сервера; ротацию ключа делаем сами |
| HashiCorp Vault (Transit) | Ключ никогда не покидает Vault, аудит | Ещё один сервис для развёртывания и изучения |
| pgcrypto в PostgreSQL | Шифрование в SQL | Ключ попадает в SQL-запросы и журналы базы |

**Выбор: AES-256-GCM в `node:crypto`; для проверки уникальности токена — `SecretVault.hash(token)`** (алгоритм — п. 2.13).

Принципы интерфейса редактора (по образцу n8n, решено 19.11 после пробного редактора):

1. Поток слева направо: вход блока слева, выходы справа с подписями. Постоянной палитры нет — блок добавляется через «+» у выхода, кнопку «+» на холсте или Tab: выезжает панель «Что дальше?» с поиском и описаниями блоков.
2. Окно настроек блока — модальное, в три колонки: «Вход» (доступные переменные и тестовые значения), «Настройки», «Выход» (что блок записывает и куда ведут выходы, предпросмотр).
3. У каждого типа блока свой цвет, иконка и форма по категории (старт, финиш, реплика, развилка, интеграция); акцентный цвет только у блоков, остальной интерфейс нейтральный.
4. Условия собираются конструктором «переменная — оператор — значение» с переключением в режим выражения; поля выражений и шаблонов с подсветкой, подсказками и результатом на тестовых значениях.
5. Ошибки проверки подсвечиваются на узле; клик по ошибке в списке переводит холст к блоку. Превью — чат в выдвижной панели, текущий блок подсвечивается на холсте.
6. Пустой сценарий — приветствие с выбором «с нуля» или шаблона (запись к врачу); отмена и повтор действий, горячие клавиши.

Превью показывает сообщения бота, подсветку текущего блока и панель переменных (UC-A-20…A-23).

## 2. Алгоритмы

### 2.1. Определение диалога по событию (UC-U-25)

**Задача.** По входящему обновлению мессенджера или вводу в превью понять, к какому боту и диалогу оно относится, и построить Event.

**Решение.** Диалог однозначно задаёт пара `botId + chatId`. `botId` берётся из маршрута webhook (бот, которому Telegram отправил обновление), а не из содержимого сообщения. `chatId` содержит префикс мессенджера, поэтому чаты разных мессенджеров не пересекаются.

```
receiveUpdate(botId, update):                       // MessengerGateway, api
  conn = найти подключение (botId, TELEGRAM)
  если секрет в заголовке ≠ секрет подключения → 401
  если бот не опубликован → ответить 200 и игнорировать
  chatId = "tg:" + update.chat.id
  userId = "tg:" + update.from.id
  если текст начинается с "/start"   → type = START_COMMAND
  иначе если это нажатие кнопки        → type = BUTTON_PRESS,
        payload = значение кнопки, sourceBlockId = блок, к которому относится кнопка
  иначе                                → type = TEXT_MESSAGE, payload = текст (пусто для фото, стикера)
  enqueue(Event{type, botId, chatId, userId, payload, sourceBlockId},
          jobId = "tg:" + botId + ":" + update.update_id)   // повторная доставка не задвоит событие
  ответить 200
```

Превью: `botId = null`, `chatId = "preview:" + идентификатор сеанса`, `channel = PREVIEW`.

**Почему так.** Ключ из маршрута нельзя подделать содержимым сообщения — это основа изоляции ботов (п. 2.12). Быстрый ответ 200 нужен, потому что Telegram повторяет доставку при ошибке или задержке, а дедупликация по `update_id` убирает дубли.

Принято по умолчанию: Telegram ограничивает данные кнопки (`callback_data`) 64 байтами, поэтому в кнопку кладём короткий код `{blockId}:{номер варианта}`. Значение берём из блока (Выбор из вариантов) или из текущей переменной-списка (Выбор из списка). По `blockId` движок распознаёт устаревшую кнопку (UC-U-13).

### 2.2. Порядок событий одного диалога при параллельной обработке разных

**Задача.** Использовать BullMQ без платных групп так, чтобы события одного диалога обрабатывались строго по порядку, а разных диалогов — параллельно (п. 2.4).

**Решено.** Очередь разбита на P = 16 разделов. Раздел выбирается по хешу ключа диалога. Каждый раздел в каждый момент обрабатывает ровно одно задание.

```
enqueue(event):                                    // EventDispatcher
  key = (event.botId ?? "preview") + ":" + event.chatId
  p   = hash(key) mod 16
  queues[p].add("event", event, { jobId, attempts: 1 })

// engine: на каждый раздел — Worker с concurrency = 1;
// глобальная конкурентность раздела = 1 (queue.setGlobalConcurrency(1)),
// чтобы при нескольких процессах engine раздел не обрабатывали двое
worker(p).process(job):
  транзакция:
    ctx = SELECT … FROM dialog_context WHERE bot_id = ? AND chat_id = ? FOR UPDATE
    DialogEngine.handleEvent(job.event, ctx)
  после фиксации: отправить накопленные сообщения, запустить HTTP-запрос (если был)
```

- Все события одного диалога попадают в один раздел и выполняются в порядке постановки.
- Разные диалоги распределены по 16 разделам и идут параллельно. В одном разделе диалоги делят очередь, но задания короткие (миллисекунды): движок не ждёт внешние системы внутри задания (п. 1.5).
- `attempts: 1`: упавшее задание не повторяется автоматически. Иначе BullMQ отложит его, и следующее событие диалога обгонит предыдущее. Ошибку движка записываем в журнал, а диалог в превью получает системное сообщение.
- Блокировка строки `FOR UPDATE` защищает контекст от одновременного изменения — например, переопубликацией (п. 2.11).
- Сообщения пользователю отправляются после фиксации транзакции. Если обработка откатилась, пользователь не получит сообщение из несохранённого состояния.

**Почему так.** Это та же модель, что разделы Kafka (ключ → раздел → строгий порядок), но на уже выбранном Redis/BullMQ. Запасной вариант на случай, если прототип П1 покажет проблемы: блокировка диалога в Redis, при которой задание занятого диалога откладывается.

### 2.3. Обработка события и автопроход (UC-U-02, SD-1, SD-2)

**Задача.** По событию и состоянию диалога выбрать use case. При автопроходе выполнять блоки без ожидания, пока диалог не дойдёт до блока, который ждёт пользователя или внешнюю систему, или до точки выхода.

```
handleEvent(event, ctx):
  если event.type = START_COMMAND          → restartDialog (UC-U-05)
  если ctx нет или ctx.state = FINISHED    → startDialog с точки входа опубликованного сценария бота (UC-U-01, U-04, U-07)
  по ctx.state:
    WAITING_USER     → ответ блоку ввода/выбора (UC-U-08…U-13); при успехе state = RUNNING, runAutopass
    WAITING_EXTERNAL → RESPONSE_RECEIVED/REQUEST_FAILED: п. 2.8, 2.9; сообщение пользователя: «Подождите, обрабатываю запрос» (UC-U-20)
    SUSPENDED        → сообщение пользователя: resume (UC-U-19)

runAutopass(ctx):
  steps = 0
  повторять:
    steps += 1
    если steps > 100:                                 // защита от бесконечного цикла
      пользователю — системное сообщение «Диалог остановлен: сценарий зациклился»
      в превью — подсветка текущего блока
      finishDialog(ctx)                               // state = FINISHED; следующее сообщение — новый диалог (UC-U-04)
      выход
    block = ctx.currentBlock
    выбор по типу block:
      EntryPoint         → out = block.getDefaultOutput()
      TextMessage        → отправить render(block.text); out = default (UC-U-21)
      Assignment         → ctx.setVariable(block.variableName, evaluate(block.expression)); out = default (UC-U-22)
      Condition          → out = evaluate(block.expression) ? «да» : «нет» (UC-U-23)
      Switch             → out = выход со значением переменной, иначе «иначе» (UC-U-24)
      ListChoice         → список = значение listVariable;
                           пуст → out = «нет вариантов» (UC-U-11);
                           иначе отправить вопрос с кнопками, state = WAITING_USER, выход
      TextInput, OptionChoice → отправить вопрос, state = WAITING_USER, выход
      HttpRequest        → createAndSend (п. 2.6), state = WAITING_EXTERNAL, выход
      ExitPoint          → finishDialog(ctx) (UC-U-03), выход
    если out.target нет → только в превью: stopAtUnconnectedOutput (UC-A-22), выход
    ctx.setCurrentBlock(out.target)
```

**Решено: лимит 100 шагов автопрохода на одно событие.** Цикл из блоков без ожидания (Присваивание → Условие → снова Присваивание) может быть осознанным счётчиком, поэтому запрещать циклы при проверке нельзя. Но цикл, который никогда не дойдёт до ввода, HTTP-запроса или точки выхода, заблокирует раздел очереди. 100 шагов с запасом покрывают любой разумный сценарий. При превышении диалог завершается (FINISHED), пользователь получает системное сообщение, в превью подсвечивается блок, на котором остановился автопроход. Следующее сообщение пользователя начинает новый диалог с точки входа, как в UC-U-04. Валидатор заранее выдаёт предупреждение о цикле без блоков ожидания, но публикацию не запрещает (п. 2.10).

### 2.4. Подстановка переменных в шаблон (UC-U-26, SD-2a)

**Задача.** Подставить значения переменных в текст сообщения, URL, заголовки и тело HTTP-запроса.

```
render(template, ctx, mode):              // mode: TEXT | URL | HEADER | JSON
  names  = extractVariableNames(template)         // /\{\{\s*([A-Za-z_][A-Za-z0-9_.]*)\s*\}\}/g
  values = для каждого имени:
             "env.ИМЯ" → окружение: бота (MESSENGER) или проекта (PREVIEW); секретное — расшифровать в памяти
             иначе     → переменная диалога
             нет значения → ""
  substitute(template, values, mode):             // один проход слева направо
    TEXT   → значение как есть
    URL    → encodeURIComponent(значение)
    HEADER → удалить переводы строк (защита от внедрения заголовков)
    JSON   → экранировать как содержимое JSON-строки (кавычки, \, переводы строк)
```

**Решено: переменные окружения записываются `{{env.ИМЯ}}`.** Префикс `env.` отделяет их от переменных диалога: имя переменной диалога не может перекрыть переменную окружения.

**Почему так (принято по умолчанию):**

- Подстановка выполняется за один проход: подставленное значение повторно не разбирается. Если пользователь введёт текст `{{env.API_KEY}}`, он не раскроется в секрет.
- Экранирование зависит от места. Ввод пользователя с `&` или `"` не ломает URL и JSON-тело запроса.
- Решено: секретные переменные окружения можно использовать везде — в HTTP-запросе, тексте сообщений, вопросах и выражениях. Ответственность за то, что секрет не попадёт пользователю, лежит на авторе. Рекомендация автору: не выводить секретные переменные в текст сообщений и вопросов.
- Отсутствующая переменная превращается в пустую строку; в превью показываем об этом предупреждение.

### 2.5. Безопасное вычисление выражений (без eval)

**Задача.** Вычислить выражения вида `tries + 1`, `tries < 3`, `status == "booked"` над переменными диалога и окружения.

**Решено.** Грамматика (подмножество JavaScript): числа, строки в кавычках, `true`/`false`, имена переменных, `{{env.ИМЯ}}`, скобки, арифметика `+ - * / %`, сравнения `== != < <= > >=`, логические `&&`, `||`, `!`. Строку разбирает `jsep`, дерево вычисляет наш интерпретатор:

```
prepare(expression):
  каждое вхождение {{env.ИМЯ}} заменяется ссылкой на переменную окружения
  (служебный идентификатор), а не её значением — значение не может изменить структуру выражения
  ast = jsep(результат)

evaluate(node, ctx):
  Literal     → node.value
  Identifier  → переменная диалога или (для ссылки env) переменная окружения
                нет переменной → ошибка «неизвестная переменная»
  Unary       → только "!" и "-"
  Binary      → только операторы из белого списка; сравнение — числовое, если обе части числа, иначе строковое
  Logical     → && и || с коротким замыканием
  любой другой узел (вызов функции, доступ к полю, присваивание, this) → ошибка «недопустимое выражение»
```

- Переменные в модели — строки. Поэтому `"10" < "9"` сравнивается как числа 10 и 9, если обе строки — числа.
- Принято по умолчанию: длина выражения до 500 символов, глубина дерева до 32.
- Выражение разбирается при проверке сценария: синтаксическая ошибка видна автору до публикации.

**Почему так.** Узлы доступа к полям и вызовов функций не исполняются вовсе. Поэтому выражение не может добраться до объектов JavaScript (`constructor`, `process`) — это главный источник уязвимостей у библиотек на `eval`/`Function`.

### 2.6. HTTP-запрос: создание и отправка (UC-U-14, SD-3)

```
createAndSend(block, ctx):                         // HttpRequestExecutor, внутри задания очереди
  [method, url, headers, body] = block.getRequestTemplate()
  [timeoutSec, retryCount, retryIntervalSec] = block.getRetryPolicy()
  request = new Request(method,
                        render(url, URL), render(headers, HEADER), render(body, JSON),
                        botId = ctx.botId, chatId = ctx.chatId, status = SENT)
  секретные заголовки и переменные окружения расшифровываются только в памяти;
  в http_request.headers пишется маска
  сохранить request; ctx.setCurrentRequest(request); ctx.setState(WAITING_EXTERNAL)
  после фиксации транзакции: apiClient.send(request, timeoutSec, retryCount, retryIntervalSec)   // без await

ExternalApiClient.send(request, timeoutSec, retryCount, retryIntervalSec):
  pRetry(попытка, { retries: retryCount, minTimeout: retryIntervalSec*1000, factor: 1 })
    попытка: ответ = undici.request(url, { method, headers, body, signal: AbortSignal.timeout(timeoutSec*1000) })
             код не 2xx → ошибка (повторяется)
    успех           → onResponse(request.id, код, тело)        → событие RESPONSE_RECEIVED
    повторы исчерпаны → onFailure(request.id, код и текст ошибки) → событие REQUEST_FAILED
```

Ошибка для повтора (п. 2.6 Use cases): код не 2xx, тайм-аут, сетевая ошибка. Ответ, который не удалось разобрать, обрабатывается движком после получения (п. 2.7) и сразу ведёт к стратегии ошибки, без повторов (SD-4 → SD-5). При повторах используется тот же Request с тем же id.

**Решено: предупреждение о повторе неидемпотентных запросов.** Если у блока метод POST, PUT или PATCH и число повторов больше 0, редактор показывает в настройках блока предупреждение: повтор может выполнить действие дважды (например, дважды забронировать слот, если первый запрос дошёл, а ответ потерялся). Решение остаётся за автором.

### 2.7. Разбор JSON-ответа по jsonPath (UC-U-15, SD-4)

**Задача.** Сохранить ответ в переменную блока и разложить нужные поля по переменным согласно ResponseMapping.

**Решение (подмножество синтаксиса принято по умолчанию):**

```
путь    := "$" сегмент*
сегмент := "." имя | "[" целое "]" | "['" строка "']"
примеры: $.slots   $.slots[0].time   $['clinic-id']   $.data.items[2].doctor.name
не поддерживаются в первой версии: *, .., фильтры ?(…), срезы [a:b]
```

```
handleResponse(ctx):                                // возвращает handled
  body = request.getResponseBody()
  ctx.setVariable(block.getVariableName(), body)    // весь ответ строкой — всегда
  mappings = block.getResponseMappings()
  если mappings пуст → перейти по «успех»; return true      // ответ не обязан быть JSON
  json = ResponseParser.parse(body)                 // JSON.parse
  если ошибка разбора → return false               // → стратегия ошибки (SD-5)
  для каждого m из mappings:
    value = ResponseParser.extract(json, m.getJsonPath())
    если путь не найден → return false              // ошибка разбора → стратегия ошибки
    ctx.setVariable(m.getVariableName(), toText(value))
  ctx.setCurrentBlock(выход «успех».target); state = RUNNING; runAutopass  // SD-2
  return true

toText(value): строка → как есть; число, логическое → String(value);
               объект, массив → JSON.stringify(value) (например, список для «Выбора из списка»); null → ""

extract(json, path): разобрать путь на сегменты; идти по объекту;
                     сегмент отсутствует или тип не тот (индекс у объекта) → «не найдено»
```

**Решено:**

- Весь ответ сохраняется в переменную блока, отдельные поля — по ResponseMapping; работают оба механизма.
- Ответ 2xx не в JSON при пустом списке ResponseMapping — не ошибка: тело сохраняется в переменную блока строкой. «Не JSON» считается ошибкой разбора, только если у блока есть правила ResponseMapping.
- jsonPath из ResponseMapping не нашёл поле — ошибка разбора; дальше работает стратегия ошибки блока.

**Почему так.**

- Своё подмножество (около 50 строк) вместо библиотеки: у популярного пакета jsonpath-plus была уязвимость удалённого выполнения кода в режиме фильтров. Фильтры автору первой версии не нужны.
- Синтаксис путей проверяется при валидации сценария.
- «Выбор из списка» получает массив как JSON-строку. Поля `labelField` и `valueField` — имена полей элемента: подпись кнопки и сохраняемое значение (UC-A-09).

### 2.8. Отбрасывание неактуальных ответов

**Задача.** Ответ на запрос, который уже не нужен (после /start, переопубликации, ошибки), не должен менять диалог (п. 2.4 Use cases, SD-4).

```
on RESPONSE_RECEIVED или REQUEST_FAILED(event):
  ctx = loadContext(event.botId, event.chatId)
  если ctx нет
     или ctx.state ≠ WAITING_EXTERNAL
     или ctx.currentRequest = null
     или ctx.currentRequest.id ≠ event.requestId:
    записать в журнал «ответ отброшен»; выход               // EventDispatcher.isStale
  иначе обработать (п. 2.7 или 2.9)
```

**Почему так.** /start (UC-U-05) и переопубликация (UC-U-07) очищают `current_request_id`, поэтому опоздавший ответ ни с чем не совпадёт. Проверка идёт внутри задания своего раздела, то есть строго после событий, сбросивших контекст. Гонка «ответ пришёл одновременно с /start» исключена порядком очереди.

### 2.9. Стратегии ошибок HTTP-блока (UC-U-16…U-19, SD-5)

| Стратегия (Use cases, п. 2.6) | Где выполняется | Что происходит |
| --- | --- | --- |
| Retry | ExternalApiClient (библиотека, п. 2.6) | До N повторов с интервалом; пользователь видит только задержку |
| Завершение диалога | Выход «ошибка» → Текстовое сообщение → Точка выхода | Код и текст ошибки в errorVariable, переход по выходу «ошибка» |
| Fallback | Выход «ошибка» → запасная ветка | То же; ветку строит автор |
| Приостановка (SUSPEND) | DialogEngine | Отправить suspendText, state = SUSPENDED; блок и переменные сохраняются |

```
handleFailure(ctx):                         // после REQUEST_FAILED или handleResponse = false
  block = ctx.currentBlock; request = ctx.currentRequest
  ctx.setVariable(block.getErrorVariable(), {"code": код или 0, "message": текст})
  выбор по block.getErrorStrategy():
    EXIT_ERROR → ctx.setCurrentBlock(выход «ошибка».target); state = RUNNING; runAutopass
    SUSPEND    → отправить block.getSuspendText(); state = SUSPENDED

resume(ctx):                                // UC-U-19: сообщение пользователя в SUSPENDED (только после HTTP-ошибки)
  request = ctx.currentRequest; request.status = SENT
  state = WAITING_EXTERNAL; после фиксации apiClient.send(request, …)   // тот же Request
```

Завершение и fallback для движка одинаковы: оба — переход по выходу «ошибка». Различается только ветка, которую построил автор. Формат переменной ошибки (`code`, `message`; `code = 0` для тайм-аута и сетевой ошибки) принят по умолчанию.

### 2.10. Правила проверки сценария (UC-A-24, A-27)

Проверка идёт в два слоя:

1. **Структура** (схема Zod) — при сохранении проекта и импорте: типы блоков, обязательные ключи, ссылки переходов на существующие блоки и выходы.
2. **Смысл** (ScenarioValidator) — по кнопке «Проверить» и перед публикацией.

**Решено:** результат проверки — список ValidationError(rule, message, severity, block). `severity` — ERROR или WARNING; предупреждения публикацию не блокируют. Ссылка на блок (`getBlock()`, в данных — `blockId`) нужна, чтобы по клику на ошибку редактор подсвечивал блок (UC-A-24, шаг 2).

| Правило | Уровень | Источник | Как проверяем |
| --- | --- | --- | --- |
| Ровно одна точка входа | ERROR | Use cases, п. 2.8 | Посчитать блоки EntryPoint: ровно 1 |
| Все выходы подключены, кроме точки выхода; включая «ошибка» при EXIT_ERROR и «нет вариантов» у Выбора из списка | ERROR | п. 2.8 | Набор выходов вычисляется по типу и настройкам блока; для каждого нужен переход из этого выхода |
| Заполнены обязательные поля: текст, имя переменной, выражение, условие, значения переключателя, источник списка, URL | ERROR | п. 2.8 | Таблица «тип блока → обязательные поля», проверка на непустоту |
| У бота есть подключение к мессенджеру (было: «к проекту подключён токен бота») | ERROR | п. 2.8 с учётом сущности Bot; `checkConnections(bot)` | У бота ≥ 1 MessengerConnection |
| Цикл без блоков ожидания | WARNING | Решено (п. 2.3) | Поиск циклов в графе, где все блоки — без ожидания (Присваивание, Условие, Переключатель, Текстовое сообщение) |
| Выражения разбираются | ERROR | Принято по умолчанию (п. 2.5) | Разобрать jsep, проверить белый список узлов |
| Шаблоны и jsonPath синтаксически верны | ERROR | Принято по умолчанию (п. 2.4, 2.7) | Разобрать `{{…}}` и пути ResponseMapping |
| Имена переменных — идентификаторы | ERROR | Принято по умолчанию | `^[A-Za-z_][A-Za-z0-9_]*$` |
| В окружении бота нет переменной, которую использует сценарий | WARNING | Принято по умолчанию | Сравнить `{{env.ИМЯ}}` сценария с Bot.environment |
| Переменная читается, но нигде не записывается; недостижимые блоки | WARNING | Принято по умолчанию | Обход графа от точки входа |

В MVP к защите входят все правила уровня ERROR и предупреждение о цикле; остальные предупреждения — после защиты (п. 5.2).

### 2.11. Публикация и переопубликация (UC-A-26, A-27, A-28, SD-6)

```
publish(project, bot) / republish(project, bot):     // PublicationController
  scenario = project.getScenario()
  errors = validator.validate(scenario) ∪ validator.checkConnections(bot)
  если среди errors есть ERROR → вернуть errors       // UC-A-27; прежняя версия бота работает без изменений
  copy = scenario.copy()                             // глубокая копия JSON; секреты остаются зашифрованными
  для каждого conn из bot.getConnections():
    token = vault.decrypt(conn.getToken())
    gateway.connectBot(bot.id, conn.messenger, token) // setWebhook; повторный вызов безопасен
  транзакция:
    UPDATE bot SET published_scenario = copy, status = PUBLISHED, published_at = now()
    если это переопубликация:                         // событие VERSION_PUBLISHED, broadcast(bot, …)
      UPDATE dialog_context SET state = FINISHED, current_block_id = NULL,
             variables = '{}', current_request_id = NULL, updated_at = now()
      WHERE bot_id = bot.id
  вернуть предупреждения (WARNING), если есть
```

**Почему так.**

- **Копия, а не ссылка.** Автор продолжает править сценарий проекта, а бот работает с замороженной копией. Публикация атомарна: одна запись JSONB в одной транзакции. Окружение бота при публикации не меняется: у бота оно своё, у проекта — тестовое.
- **Сброс контекстов одним UPDATE** вместо события на каждый диалог. Результат тот же, что у VERSION_PUBLISHED для каждого диалога (UC-U-07), но за одну операцию. Задание, которое в этот момент обрабатывает диалог, держит блокировку строки (п. 2.2), поэтому UPDATE дождётся его завершения. Следующее событие увидит FINISHED и начнёт диалог с точки входа новой версии. Опоздавшие HTTP-ответы будут отброшены (п. 2.8).
- **Подключение до фиксации** (принято по умолчанию). Если setWebhook не удался, статус бота не меняется, и автор видит ошибку.

**Решено: подключение мессенджера с проверкой уникальности токена** (UC-A-25, `connectMessenger(bot, messenger, token)`):

```
connectMessenger(bot, messenger, token):
  если gateway.verifyToken(messenger, token) = false → ошибка «токен недействителен» (альтернатива 1а)
  h = vault.hash(token)
  если есть messenger_connection с token_hash = h и другим bot_id
     → ошибка «токен уже используется другим ботом» (новая альтернатива UC-A-25)
  secret = vault.encrypt(token)
  сохранить messenger_connection(bot_id, messenger, token_cipher, token_mask, token_hash = h)
```

Один токен Telegram может обслуживать только одного бота: у токена один webhook. По шифротексту уникальность не проверить (из-за случайного IV он каждый раз разный), поэтому хранится отдельный хеш с ограничением UNIQUE.

### 2.12. Изоляция ботов (multi-tenancy)

Цель (семинар 28.10): один сценарий обслуживает нескольких клиентов, например боты записи в поликлинику для разных городов с разными базами. Данные клиентов не должны смешиваться.

| Что изолировано | Как обеспечивается |
| --- | --- |
| Сценарий | У каждого бота своя копия `published_scenario`; переопубликация одного бота не трогает других |
| Переменные окружения (адрес API, ключи клиента) | `bot.environment`; в шаблоны подставляется окружение только бота текущего диалога; секретные значения зашифрованы. Превью использует отдельное тестовое окружение проекта |
| Токены мессенджеров | `messenger_connection` с внешним ключом на бота; один токен — один бот (`token_hash` UNIQUE) |
| Диалоги | Ключ контекста `(bot_id, chat_id)`: один и тот же пользователь Telegram в двух ботах — два независимых диалога |
| Входящие события | `botId` берётся из маршрута webhook и проверяется секретом подключения, а не из содержимого сообщения |
| Доступ авторов | Все запросы API фильтруются по `project.author_id` текущего автора; бот доступен через свой проект |

**Почему так.** Изоляция задаётся данными (разные строки и ключи), а не условиями в сценарии. Куратор отметил, что проверки внутри сценария легко ошибочно написать, а здесь бот физически не видит чужих переменных и диалогов.

### 2.13. Шифрование секретов (SecretVault)

Что шифруется: токены мессенджеров, секретные заголовки HTTP-блока, секретные переменные окружения (EnvironmentVariable с `secret = true`) у бота и у проекта.

```
encrypt(value, aad):
  iv  = randomBytes(12)
  c   = createCipheriv("aes-256-gcm", KEY, iv); c.setAAD(aad)
  ct  = c.update(value) + c.final(); tag = c.getAuthTag()
  cipherText = "v1:" + b64(iv) + ":" + b64(tag) + ":" + b64(ct)
  mask = "••••" + последние 4 символа value
  вернуть EncryptedSecret{cipherText, mask}

decrypt(secret, aad): разобрать версию, iv, tag, ct; setAuthTag(tag); при несовпадении — ошибка

hash(token): HMAC-SHA-256(HASH_KEY, token) в hex       // для messenger_connection.token_hash
```

- `KEY` и `HASH_KEY` — по 32 байта из переменных окружения сервера; их нет ни в базе, ни в репозитории. Префикс `v1` — версия ключа для будущей ротации.
- Для каждого секрета новый случайный IV: одинаковые токены дают разные шифротексты. Поэтому для уникальности используется детерминированный `hash`.
- Принято по умолчанию: AAD — идентификатор владельца (`bot_id:messenger` для токена, `bot_id` или `project_id` + имя переменной для окружения). Шифротекст, перенесённый в чужую строку, не расшифруется.
- Маска вычисляется при записи (`token_mask`, `mask` у переменной), поэтому для показа в редакторе расшифровывать не нужно. API никогда не возвращает расшифрованное значение.
- Расшифровка — только в памяти engine/api в момент подстановки в шаблон или выражение, отправки HTTP-запроса или вызова `connectBot`. В журналах секреты заменяются маской.
- Экспорт сценария не содержит секретов, в том числе секретных переменных окружения (UC-A-29); после импорта их вводят заново (UC-A-30).

## 3. Модель данных

### 3.1. Таблицы PostgreSQL

Таблицы соответствуют ER-диаграмме в `chatbot.vpp`.

| Таблица | Столбцы | Ключи и ограничения |
| --- | --- | --- |
| author | id, email, password_hash, created_at | PK id; UNIQUE email |
| project | id, author_id, name, scenario JSONB, environment JSONB, updated_at | PK id; FK author_id → author; environment — тестовое окружение для превью |
| bot | id, project_id, name, status, published_scenario JSONB NULL, environment JSONB, published_at NULL | PK id; FK project_id → project; status ∈ {CREATED, PUBLISHED} |
| messenger_connection | id, bot_id, messenger, token_cipher, token_mask, token_hash | PK id; FK bot_id → bot; UNIQUE (bot_id, messenger); UNIQUE token_hash; messenger ∈ {TELEGRAM, VK} |
| dialog_context | id, bot_id NULL, chat_id, user_id, channel, state, current_block_id, variables JSONB, current_request_id NULL, updated_at | PK id; FK bot_id → bot (NULL для превью); FK current_request_id → http_request; UNIQUE (bot_id, chat_id) |
| http_request | id, dialog_context_id, block_id, method, url, headers JSONB, body, status, response_code NULL, response_body NULL, error NULL, created_at | PK id; FK dialog_context_id → dialog_context; status ∈ {SENT, SUCCEEDED, FAILED, TIMED_OUT} |

Очередь событий живёт в Redis (BullMQ), не в базе.

Соответствие классам модели:

| Класс | Где хранится |
| --- | --- |
| Author, Project, Bot, MessengerConnection, DialogContext, Request | Одноимённые таблицы |
| EnvironmentVariable | JSONB-массив: project.environment (тестовое), bot.environment (рабочее); у секретной переменной — шифротекст и маска вместо значения |
| EncryptedSecret | Столбцы token_cipher и token_mask; для секретных заголовков и переменных окружения — внутри JSON |
| Scenario, Block, Output, Transition, HttpHeader, ResponseMapping | JSONB: project.scenario и bot.published_scenario |
| Variable | JSONB: dialog_context.variables |
| Event | Задание в Redis |
| ValidationError | Не хранится: вычисляется при проверке |

Замечания к схеме:

- `dialog_context` и `http_request` ссылаются друг на друга. Это допустимо: `current_request_id` может быть NULL, и запрос создаётся после контекста.
- Для превью `bot_id = NULL`. В PostgreSQL значения NULL в UNIQUE не считаются равными, поэтому сеансы превью не конфликтуют; уникальность даёт `chat_id = "preview:<сеанс>"`.
- `current_block_id` — идентификатор блока внутри JSON сценария, а не внешний ключ (следствие решения 3.2).
- Принято по умолчанию: индексы `http_request(dialog_context_id)` и `http_request(status, created_at)` — для восстановления после перезапуска (п. 1.5).
- Принято по умолчанию: `response_body` ограничен 1 МБ; журнал `http_request` старше 30 дней удаляется.

### 3.2. Сценарий: JSONB или нормализация

**Решено: сценарий хранится целиком как JSONB** — граф блоков и переходов в одном значении: `project.scenario` для редактирования, `bot.published_scenario` для работы бота.

| Критерий | JSONB целиком | Нормализация (таблицы block, output, transition, http_header, response_mapping) |
| --- | --- | --- |
| Публикация копией (SD-6) | Одно присваивание `published_scenario = scenario` в транзакции | Копирование строк пяти таблиц с переназначением ключей |
| Версионирование, история | Версия — это значение JSON; легко хранить снимки | Нужны версии у каждой строки или копии таблиц |
| Сохранение из редактора | Редактор (React Flow) держит граф целиком и сохраняет одним запросом | Вычислять разницу и синхронизировать строки |
| Импорт/экспорт (UC-A-29/30) | Формат файла почти совпадает с форматом хранения | Сборка и разборка графа из таблиц |
| Проверка формата | Схема Zod / JSON Schema — одна для API, редактора, движка и импорта | Ограничения БД + отдельная проверка графа |
| Чтение движком | Одна строка бота; граф в памяти на время задания | Несколько запросов или JOIN на каждое событие |
| Запросы «по блокам» (найти все HTTP-блоки с URL …) | Неудобно (возможно через `jsonb_path_query`) | Удобно; но таких use case нет |
| Ссылочная целостность внутри графа | Нет: переход может ссылаться на несуществующий блок — ловит схема и валидатор | Внешние ключи гарантируют |
| Изменение формата | Нужны миграции JSON: поле `formatVersion` и функция «обновить с версии N» | Обычные миграции SQL |

**Почему JSONB.** Сценарий читается и пишется только целиком: редактор сохраняет граф, публикация копирует граф, движок загружает граф бота. Ни один use case не запрашивает отдельные блоки из базы. Главный минус — нет ссылочной целостности внутри графа. Его закрывает проверка схемой при каждом сохранении и импорте плюс валидатор перед публикацией. Второй минус — эволюция формата. Её закрывает поле `formatVersion` и функции миграции в `packages/model`.

### 3.3. Формат сценария и окружения (набросок)

Формат принят по умолчанию; поля повторяют диаграмму «Классы: блоки сценария».

```json
{
  "formatVersion": 1,
  "blocks": [
    { "id": "b1", "type": "ENTRY_POINT", "title": "Старт", "x": 0, "y": 0 },
    { "id": "b2", "type": "TEXT_INPUT", "title": "ФИО", "x": 240, "y": 0,
      "question": "Как вас зовут?", "variableName": "fio" },
    { "id": "b3", "type": "HTTP_REQUEST", "title": "Слоты", "x": 480, "y": 0,
      "method": "GET", "url": "{{env.API_URL}}/slots?clinic={{clinic}}",
      "headers": [ { "name": "Authorization", "value": "Bearer {{env.API_KEY}}", "secret": false } ],
      "body": "", "variableName": "slotsResponse", "errorVariable": "slotsError",
      "timeoutSec": 10, "retryCount": 2, "retryIntervalSec": 5,
      "errorStrategy": "EXIT_ERROR", "suspendText": null,
      "responseMappings": [ { "jsonPath": "$.items", "variableName": "slots" } ] }
  ],
  "transitions": [
    { "source": { "blockId": "b1", "output": "default" }, "target": "b2" },
    { "source": { "blockId": "b2", "output": "default" }, "target": "b3" }
  ]
}
```

Окружение (bot.environment или project.environment):

```json
[
  { "name": "API_URL", "value": "https://clinic-test.example/api", "secret": false },
  { "name": "API_KEY", "secret": true, "secretValue": { "cipherText": "v1:…", "mask": "••••a1b2" } }
]
```

## 4. Что требует прототипирования

Решения разделов 1–3 приняты без прототипа: язык, фреймворки, база, очередь из 16 разделов, шифрование, грамматика выражений и jsonPath. До защиты остаётся три спринта, поэтому прототипы сокращены до коротких проверок в первом спринте. Каждая проверка либо подтверждает решение, либо включает запасной вариант. Отдельных нагрузочных испытаний до защиты не проводим.

| № | Что проверяем | Поток, срок | Критерий успеха | Если не прошло |
| --- | --- | --- | --- | --- |
| П1 | Очередь из 16 разделов сохраняет порядок; HTTP-запросы с повторами вне задания не тормозят другие диалоги; после перезапуска engine запросы уходят в FAILED | Движок и HTTP, спринт 1, около половины дня | 200 диалогов по 10 перемешанных событий — 0 нарушений порядка; при 50 «зависших» запросах (тайм-аут 10 с) события других диалогов обрабатываются без задержки; после перезапуска диалоги выходят из WAITING_EXTERNAL по стратегии ошибки | Блокировка диалога в Redis вместо разделов (п. 2.2) |
| П2 | Webhook Telegram через очередь: маршрут `/webhook/telegram/{botId}`, секрет в заголовке, туннель для локальной разработки | API, данные, Telegram; спринт 1 | Эхо-бот отвечает через очередь; запрос без секрета отклоняется; повторная доставка не задваивает событие | Long polling для разработки; webhook только на сервере |
| П3 | Холст React Flow — первая итерация самого редактора, а не отдельный выбрасываемый прототип | Фронтенд, спринт 1 | Участник команды, не писавший холст, собирает сценарий записи к врачу; JSON после сохранения и загрузки не меняется | Упростить узлы, отложить мини-карту и прочие удобства |

Проверка изоляции двух ботов одного сценария — часть приёмки спринта 2, а не отдельный прототип.

## 5. План реализации

### 5.1. Допущения

- Команда — 4 человека, каждый уделяет проекту около одного дня в неделю (семинар 28.10).
- **Спринт — 2 недели, то есть 2 рабочих дня каждого участника; за спринт команда даёт около 8 человеко-дней.** В конце спринта — показ работающего результата.
- Защита — в конце декабря 2026; точную дату уточним. С 18.11 до защиты — 3 спринта, всего около 24 человеко-дней. Резервного спринта нет, поэтому к защите делается урезанный MVP (п. 5.2), а при отставании работа срезается в заранее заданном порядке (п. 5.5).
- Четыре параллельных потока — по числу участников (п. 5.3). Лид собирает результаты спринтов в дополнение к своему потоку.

### 5.2. Состав MVP к защите

Цель MVP — эталонный сценарий записи к врачу: собран в редакторе, проверен в превью, опубликован, отвечает в Telegram, обращается к внешнему API, выгружается в файл и загружается обратно. Так MVP закрывает все четыре обязательных критерия успеха из Vision.

**Входит в MVP:**

| Область | Что входит | UC / SD |
| --- | --- | --- |
| Личный кабинет (минимум) | Регистрация, вход, создание и открытие проекта | UC-A-01, A-02, A-03; A-04 частично |
| Редактор (минимум) | Холст, 10 типов блоков с простыми формами настроек, переходы, удаление; предупреждение о повторе POST/PUT/PATCH | UC-A-05…A-19 |
| Окружения | Рабочее окружение бота и тестовое окружение проекта, секретные переменные с маской | Bot.environment, Project.environment |
| Превью (полное) | Окно чата через тот же движок с тестовым окружением проекта; подсветка текущего блока; панель переменных; остановка на неподключённом выходе; перезапуск | UC-A-20, A-21, A-22, A-23 |
| Проверка и публикация | Создание бота, подключение Telegram с проверкой уникальности токена, проверка сценария (все правила ERROR и предупреждение о цикле) с подсветкой блока, публикация, переопубликация со сбросом контекстов | UC-A-24…A-28, A-32; UC-U-07; SD-6 |
| Экспорт и импорт | Экспорт сценария в JSON без секретов; импорт JSON с проверкой схемы и сообщением об ошибке | UC-A-29, A-30, A-31 |
| Движок | Очередь из 16 разделов, определение диалога, автопроход с лимитом, все блоки без HTTP, выражения и шаблоны с `{{env.ИМЯ}}` | UC-U-01…U-13, U-21…U-26; SD-1, SD-2, SD-2a |
| HTTP-блок | Отправка с тайм-аутом и повторами, разбор ответа и ResponseMapping, стратегии ошибок, отбрасывание неактуальных ответов, восстановление после перезапуска | UC-U-14…U-20; SD-3, SD-4, SD-5 |
| Telegram | Webhook, отправка сообщений и кнопок | MessengerGateway |
| Инфраструктура | Docker Compose, CI, VPS с Caddy (HTTPS, Let's Encrypt) | — |

**Не входит в MVP (после защиты или по остатку времени):**

| Что | UC / SD | Почему откладываем |
| --- | --- | --- |
| YAML при экспорте и импорте | UC-A-29, A-30 (частично) | JSON закрывает требование Vision; YAML — второй формат того же содержания |
| VK | MessengerType.VK | Решено: до защиты только Telegram |
| Предупреждения валидатора, кроме цикла: переменная не записывается, недостижимые блоки, переменной нет в окружении бота | — | Вытеснены полным превью и импортом/экспортом; ошибки ERROR проверяются все |
| Удаление и переименование проектов, удобства редактора (мини-карта, горячие клавиши) | UC-A-04 (частично) | Не влияет на сценарий записи к врачу |
| Сквозные тесты Playwright, нагрузочные испытания | — | Не успеваем; до защиты — модульные тесты движка |

**Что вытеснено, чтобы поместились полное превью и импорт/экспорт JSON:**

- три предупреждения валидатора (таблица выше) — после защиты;
- отдельное время на исправление ошибок у потока 2 в спринте 3 — он берёт экспорт и импорт;
- Socket.IO-шлюз переходит от потока 3 к потоку 1: поток 3 в спринте 3 занят публикацией и страницей ботов;
- развёртывание на VPS переносится из спринта 3 в спринт 2, чтобы в последнем спринте не настраивать сервер.

Почему такой порядок:

- Первыми идут проверки самых рискованных частей (очередь, HTTP вне задания, webhook) — от них зависит архитектура движка.
- Движок и HTTP готовы ко второму спринту, потому что публикация и превью используют их без изменений.
- События превью движок начинает публиковать уже во втором спринте, чтобы в третьем фронтенд подключал готовый канал.
- Фронтенд с первого спринта идёт параллельно и не ждёт API: формат сценария общий (`packages/model`).

### 5.5. Риски плана

| Риск | Что делаем |
| --- | --- |
| Не успеваем к защите: резервного спринта нет, а спринт 3 загружен плотно | Срезаем в таком порядке: переопубликация (остаётся первая публикация) → предупреждение валидатора о цикле → формы редкоиспользуемых блоков (Переключатель) → панель переменных превью. Экспорт и импорт JSON и остальное превью не срезаем: они закрывают критерии Vision |
| Один день в неделю — длинные перерывы, теряется контекст | Задачи не больше одного дня, заметки в задачах, обязательный показ в конце спринта |
| Участник пропустил день | У каждого потока есть помощник (раздел 6); общий формат в `packages/model` позволяет подменять друг друга |
| П1 показал проблемы с порядком | Запасной вариант — блокировка диалога в Redis (п. 2.2) |
| VPS не готов во втором спринте | До его готовности — туннель или long polling; развёртывание не позже начала спринта 3 |
